## 两层缓冲

```text
printf / fwrite
       ↓
C 库的用户态缓冲
       ↓ 刷新时通过底层写入接口提交
内核管理的普通文件缓存
       ↓ 回写或同步
存储设备
```

write 使用 fd，绕过 stdio 的用户态缓冲，但普通文件写入仍可能经过内核缓存。printf 使用 stdout 流，stdout 是 FILE*；FILE 对象由 C 库维护，除了底层描述符还管理缓冲与流状态。文件描述符层的 open/read/write/close 对应整数 fd；stdio 层的 fopen/fread/fwrite/fclose 对应 FILE*，不应混淆两组接口的参数与返回值。

输出缓冲有无缓冲、行缓冲、全缓冲三类。glibc 的 stdout 连到终端时通常行缓冲，重定向到普通文件时通常全缓冲。行缓冲遇到换行会提交数据；全缓冲中的换行通常不触发刷新，缓冲区满、显式刷新、关闭流或正常退出等才会提交数据。

fflush(stdout) 提交 C 库尚未输出的数据；成功返回 0，失败返回 EOF 并设置 errno。它处理用户态缓冲，不等于 fsync(fd) 所请求的文件存储同步。对 stdio 文件需要先成功 fflush，再通过 fileno 获得 fd 并 fsync，才有机会同步刚才还留在 C 库中的内容。持久化创建、重命名等目录变化还涉及目录同步，后续文件系统章节展开。

从 main 正常返回或调用 exit 会刷新输出流。SIGKILL、默认终止信号、_exit 等路径不提供这一 stdio 刷新保证；内核在进程结束时关闭 fd，并不能替该进程把用户态缓冲中尚未提交的字节补写出来。这个问题与信号章节的“由主流程正常退出”有关。

同一底层文件交替使用 stdio 和描述符操作需要协调缓冲与文件位置。入门实验采用各自一致的接口，不用混合输出顺序作为可移植保证。

## 源码逻辑

程序的两个模式均先 printf 输出 `HELLO\n`（6 字节）。flushed 模式立即 fflush(stdout)；buffered 模式保留默认缓冲行为。随后 stderr 打印就绪日志并 sleep 30 秒，给学习者观察文件的时间。最后从 main 正常返回。

strcmp 返回 0 表示两字符串相等。程序校验命令行模式，错误时打印用法并返回 2。stderr 日志用于确认 printf 已执行，不混入重定向后的 stdout 文件。

## COM12：默认缓冲

先读完这组步骤，再逐条执行。看到 sleeping 日志后，在 30 秒结束前检查文件。

```sh
cd /root/linux-study/03_file_io/06_buffer
chmod +x buffer_demo
./buffer_demo buffered > buffered.txt &
study_pid=$!
sleep 1
ls -l buffered.txt
wait "$study_pid"
echo $?
ls -l buffered.txt
cat buffered.txt
```

预期睡眠期间文件大小 0；正常结束后大小 6，内容 HELLO 加换行。wait 的状态应为 0。如果观察前程序已经结束，应重新启动这组实验，避免把退出后的大小当成睡眠期间的大小。

## COM12：显式刷新

```sh
cd /root/linux-study/03_file_io/06_buffer
./buffer_demo flushed > flushed.txt &
study_pid=$!
sleep 1
ls -l flushed.txt
wait "$study_pid"
echo $?
cat flushed.txt
```

预期睡眠期间文件大小已为 6。fflush 让另一进程可以读到数据，但这个观察不能证明数据已经落到存储介质。

如果逐条输入时错过了运行期间的观察，可在当前 06_buffer 目录把下面一整行执行：

```sh
./buffer_demo flushed > flushed.txt & study_pid=$!; sleep 1; jobs; ls -l flushed.txt
```

`&` 后 Shell 继续执行后面的命令，立即保存 PID；分号分隔按顺序执行的命令。预期 jobs 显示 Running，同时文件大小为 6。随后单独执行 `wait "$study_pid"`，再立即用 `echo $?` 查看退出状态。

## 文件可见与持久化的边界

printf 成功可能只更新进程内的 C 库缓冲；fflush 成功将这些字节提交到流的底层写入接口。对普通文件，write 成功后的数据可以被其他进程读到，但仍可能留在内核缓存。

fsync(fd) 请求将指定文件已修改的数据及相关元数据同步到存储设备，并等待设备报告完成；成功返回 0，失败返回 -1 并设置 errno。close 和 fclose 不替代这一文件同步请求。

使用 fd 接口时，成功路径是完成 write，再 fsync，最后 close。使用 stdio 时，成功路径是 fflush(fp)，通过 fileno(fp) 得到描述符并 fsync，最后 fclose(fp)。各调用都需要检查结果；直接 fsync 不能提交仍留在 C 库缓冲中的文字。

创建或重命名文件还涉及父目录项的持久化，可能需要同步父目录；fsync 也不等于让一组多次更新成为原子事务。这些问题在后续文件系统与配置保存章节展开。
