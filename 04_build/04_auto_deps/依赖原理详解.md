# 自动依赖原理：从头文件到重新构建

当前实验已执行成功。本笔记用于补齐理解，不增加新实验，也不推进下一章。

## 先区分工具与文件

| 名称 | 本节职责 |
|---|---|
| main.c、io_utils.c | C 源码 |
| io_utils.h、app_message.h | 被源码包含的头文件 |
| GCC | 编译源码；同时可记录实际依赖 |
| .o | 编译得到的目标文件，最后参与链接 |
| .d | 编译器生成的文本依赖规则，不参与链接 |
| make | 读取规则、比较时间戳、决定执行命令 |
| Makefile | 提供构建规则、变量、配方，读入 .d |

## 1. 为什么头文件变化需要重编译

main.c 中有：

~~~c
#include "app_message.h"
const char message[] = APP_MESSAGE;
~~~

app_message.h 中定义：

~~~c
#define APP_MESSAGE "Hello from Linux file I/O!\n"
~~~

预处理会处理包含与宏展开，使编译器看到的内容相当于：

~~~c
const char message[] = "Hello from Linux file I/O!\n";
~~~

所以 main.o 的生成材料包含 main.c 以及它实际包含的头文件。若头文件中的消息或声明改变，原来的 .o 可能已经过时；运行程序不会重新展开磁盘上的头文件来替换旧代码。

io_utils.c 没有包含 app_message.h，这个头文件的变化不会改变本节 io_utils.c 的编译输入。两个模块都包含 io_utils.h，因此公共头文件变化会影响两者。

## 2. 谁能确定包含了哪些文件

GCC 在预处理时需要实际读取 #include 的文件，知道展开后的依赖。make 本节不解析 C 的 #include，它需要由规则得到依赖信息。

以前手写规则 %.o: %.c io_utils.h，告诉 make 所有这些 .o 都依赖 io_utils.h。现在 GCC 用 -MMD 输出实际头文件依赖，make 再使用它。

## 3. 一次编译有两种产物

~~~sh
arm-linux-gnueabihf-gcc -std=c11 -Wall -Wextra -MMD -MP -c main.c -o main.o
~~~

生成：

- main.o：代码、数据、符号等目标文件内容，供链接使用。
- main.d：依赖列表，给 make 使用。

main.d 的第一行：

~~~make
main.o: main.c io_utils.h app_message.h
~~~

含义是 main.o 依赖冒号后面这三个文件。它是构建规则片段，不是 C 代码，不是运行日志。

同理 io_utils.d 表明：

~~~make
io_utils.o: io_utils.c io_utils.h
~~~

## 4. 生成 .d 后，还要让 make 读取它

~~~make
DEPS := $(OBJECTS:.o=.d)
-include $(DEPS)
~~~

本例 OBJECTS 是 main.o io_utils.o，DEPS 得到 main.d io_utils.d。-include 的作用是让 make 读入这些文件的规则；并不是 C 的 #include。

make 得到依赖列表，同时从模式规则取得生成 .o 的配方。效果相当于它知道：

~~~make
main.o: main.c io_utils.h app_message.h
	arm-linux-gnueabihf-gcc -std=c11 -Wall -Wextra -MMD -MP -c main.c -o main.o
~~~

实际工程仍使用通用模式规则，避免重复写配方。

只有 -MMD 而没有读入 .d，编译器虽然留下了依赖清单，但 make 没有从这份清单获得头文件依赖。依赖的生成和使用是两个环节。

## 5. 对照本次两次更新

假设完成构建后，已有 main.o、io_utils.o 和 file_app。随后 touch app_message.h，只改变它的修改时间。

main.d 告诉 make：app_message.h 是 main.o 的依赖。现在该头文件比 main.o 新，因此 main.o 需要重新生成。

io_utils.d 没有 app_message.h，io_utils.o 的依赖都没有变新，因此可以复用它。

main.o 更新之后，file_app 的一个输入更新，所以执行链接。链接仍使用两个 .o，只是其中一个重新编译，另一个复用。

随后 touch io_utils.h：两个 .d 都把它列为依赖，所以两个 .o 都重编译，再链接。

make 在这里比较存在性与时间戳；touch 不改内容仍触发构建，正说明它没有通过比较源码内容或语义来判断。

## 6. 为什么首次没有 .d 也能构建

1. make 启动时读 Makefile，-include 允许尚不存在的 .d 文件缺失。
2. file_app 和两个 .o 尚不存在，按模式规则进行完整构建。
3. 编译器生成 .o，也生成对应 .d。
4. 后续调用 make 时，已有 .d 被读入，提供完整头文件依赖。

因此没有先生成 .d 才能首次编译的循环。使用本节规则时，单独删除 .d 而保留最新 .o 不一定重建它；干净构建会一起生成两类文件。

## 7. 四个符号各自的作用

| 写法 | 作用 |
|---|---|
| -MMD | 正常编译时附带生成用户头文件依赖 |
| -MP | 为头文件生成空规则，帮助处理旧依赖里已删除或改名的头文件 |
| .o=.d | 对文件列表做后缀替换 |
| -include | 让 make 读入 .d；不存在时允许继续 |

main.d 后面的 io_utils.h:、app_message.h: 来自 -MP。没有配方，所以不会执行一个名为 io_utils.h 的命令，也不会因此把头文件编译成程序。

它们的主要用途出现在旧依赖文件仍提到已删除头文件的情况。-MP 不能修复源码仍包含缺失头文件的错误，GCC 仍会报找不到头文件。单纯 touch 的本次实验没有触发这个辅助机制。

## 当前理解目标

能用自己的话串起：头文件参与预处理 → GCC 生成 .o 与 .d → make 读入 .d → 比较目标和依赖的时间戳 → 按需编译和链接。
